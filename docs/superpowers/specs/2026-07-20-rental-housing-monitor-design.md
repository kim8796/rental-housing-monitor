# 서울·경기 공공임대주택 공고 모니터 설계

## 목표

매일 한국시간 12시에 LH, SH, GH의 공식 소스에서 서울특별시와 경기도의 행복주택, 국민임대, 신혼부부 대상 매입임대 모집공고를 확인하고, 이전 실행에서 없던 공고 또는 이전 전송에 실패한 공고만 Telegram으로 알린다. 신규 공고가 없는 정상 실행도 명시적으로 알리고, 기관별 수집 또는 파싱 실패는 해당 기관을 식별해 알린다.

## 범위

- 독립 프로젝트 경로: 애플리케이션 파일은 `rental-housing-monitor/`. GitHub가 인식해야 하는 워크플로 파일만 저장소 루트의 `.github/workflows/`에 둔다.
- 대상 기관: LH(한국토지주택공사), SH(서울주택도시개발공사), GH(경기주택도시공사)
- 대상 지역: 서울특별시, 경기도
- 대상 공급유형: 행복주택, 국민임대, 신혼부부 대상 매입임대
- 실행 환경: Python 3.12, GitHub Actions, SQLite, Telegram Bot API
- 비대상: 청년 전용 매입임대, 일반 매입임대, 전세임대, 분양, 상가, 당첨자 발표와 계약 결과 등 입주자 모집이 아닌 후속 게시물

## 공식 데이터 소스

기관별 공식 소스 혼합 방식을 사용한다.

- LH: 한국토지주택공사가 공공데이터포털에서 제공하는 `한국토지주택공사_분양임대공고문 조회 서비스`(공공데이터 ID `15058530`). `DATA_GO_KR_SERVICE_KEY`가 필요하다.
- SH: SH 인터넷청약시스템의 공식 `주택임대` 공고 게시판과 상세 페이지.
- GH: GH 주택청약·임대센터의 공식 `임대주택` 및 `매입임대` 공고 게시판과 상세 페이지.

검색엔진 결과, 비공식 커뮤니티, 제3자 재게시 데이터는 사용하지 않는다. 목록만으로 필수 필드를 채울 수 없으면 같은 기관의 공식 상세 페이지를 조회한다.

## 아키텍처

각 기관 수집기는 공통 인터페이스 `collect() -> list[Announcement]`를 구현한다. 수집기는 기관별 JSON 또는 HTML 응답을 공통 `Announcement` 모델로 정규화하고, 오케스트레이터는 수집 결과를 필터링한 뒤 SQLite와 비교하여 Telegram 전송 및 실행 결과 기록을 조정한다.

```text
LH 공식 API ─┐
SH 공식 게시판 ├─ 수집기 → Announcement → 조건 필터 → SQLite → Telegram
GH 공식 게시판 ┘
```

구성 단위는 다음과 같다.

- `models.py`: 공통 공고 및 수집 실패 모델
- `collectors/base.py`: 수집기 프로토콜과 파싱 구조 오류
- `collectors/lh.py`: LH 공식 API 호출과 JSON 정규화
- `collectors/sh.py`: SH 목록·상세 HTML 파싱
- `collectors/gh.py`: GH 임대·매입임대 목록·상세 HTML 파싱
- `filters.py`: 지역, 공급유형, 모집공고 여부 필터와 대상 분류
- `repository.py`: SQLite 스키마, 신규 판별, 확인 시각과 전송 이력 관리
- `telegram.py`: Telegram 메시지 작성, 분할, 전송
- `runner.py`: 재시도, 기관별 격리, 실행 요약, 저장 순서 조정
- `config.py`: 환경변수 검증
- `logging_config.py`: 파일 및 콘솔 로그 설정

## 공통 데이터 모델

`Announcement`는 다음 필드를 가진다.

- `source_id`: 기관이 제공하는 공고 고유번호. 없으면 `None`.
- `title`: 공고 제목
- `agency`: `LH`, `SH`, `GH` 중 하나
- `region`: `서울특별시`, `경기도`, 또는 두 지역을 쉼표로 결합한 값
- `housing_type`: `행복주택`, `국민임대`, `신혼부부 매입임대` 중 하나
- `target`: 공고에서 확인되는 입주 대상. 명시되지 않으면 공급유형에서 확정 가능한 최소 표현을 사용한다.
- `announcement_date`: 공고일
- `application_start_date`: 접수 시작일. 공식 페이지에 없으면 `None`.
- `application_end_date`: 접수 종료일. 공식 페이지에 없으면 `None`.
- `url`: 기관 공식 상세 페이지 URL

고유 키는 기관과 `source_id`를 결합한 값을 우선 사용한다. 고유번호가 없으면 추적 파라미터를 제거하고 정규화한 공식 URL의 SHA-256을 사용한다. 제목 변경만으로 같은 공고를 신규로 다시 보내지 않는다.

## 분류 및 필터링

지역은 공식 응답의 지역 필드를 우선 사용하며, 필드가 없을 때만 제목과 상세 본문의 명시적 지역 표현으로 보완한다. 서울 또는 경기 외 지역만 포함된 공고는 제외하고, 여러 지역을 포함하는 공고는 서울이나 경기를 포함하면 수집한다.

공급유형은 공식 분류값을 우선하고 제목을 보조 신호로 사용한다.

- `행복주택`: 공식 유형 또는 모집공고 제목이 행복주택을 명시
- `국민임대`: 공식 유형 또는 모집공고 제목이 국민임대를 명시
- `신혼부부 매입임대`: 매입임대이면서 제목이나 공식 대상 정보에 `신혼`, `신생아`, `신혼부부` 중 하나가 명시

`당첨`, `결과`, `계약`, `서류심사 대상자`, `예비자 발표`, `정정 결과`만을 알리는 후속 게시물은 제외한다. `모집`, `입주자`, `예비입주자`, `추가모집`, `정정공고` 중 하나를 포함한 실제 모집공고는 허용한다. 정정공고가 원 공고와 다른 기관 고유번호를 가지면 별도 신규 공고로 취급한다.

## 저장과 중복 전송 방지

SQLite에는 다음 테이블을 둔다.

- `announcements`: 고유 키, 모든 정규화 필드, 최초 발견 시각, 마지막 확인 시각
- `deliveries`: 고유 키, Telegram chat ID, 전송 성공 시각, Telegram message ID
- `runs`: 실행 시작·종료 시각, 기관별 성공 여부, 신규 수, 전체 상태

첫 실행에서는 필터에 맞는 현재 조회 결과를 모두 신규로 취급한다. 공고는 발견 즉시 `announcements`에 upsert하되, Telegram 전송이 성공한 경우에만 `deliveries`를 기록한다. 다음 실행에서 공고가 이미 존재해도 해당 chat ID의 성공 기록이 없으면 다시 전송한다. 이 순서로 전송 실패 후 영구 누락과 성공 공고의 중복 전송을 모두 막는다.

SQLite 파일은 GitHub Actions 실행 시작 시 `data` 브랜치의 `rental-housing-monitor/data/announcements.db`에서 가져오고 실행 후 변경된 DB 파일만 `data` 브랜치에 커밋·푸시한다. 워크플로는 `contents: write` 권한과 `concurrency` 그룹을 사용해 동시에 두 실행이 DB를 갱신하지 못하게 한다. 애플리케이션 코드는 기본 브랜치에만 있고, `data` 브랜치는 DB 영속화 전용이다.

## 실행 결과와 Telegram 메시지

신규 공고 메시지는 제목, 기관, 지역, 공급유형, 대상, 공고일, 접수기간, 공식 URL을 포함한다. 날짜가 공식 소스에 없으면 `정보 없음`으로 표시한다. Telegram 길이 제한을 넘으면 공고 단위로 여러 메시지로 분할한다.

모든 기관 수집이 정상이고 신규 공고가 0건이면 다음 메시지를 보낸다.

```text
오늘은 신규 공고가 없습니다.
```

일부 기관이 실패하면 정상 기관의 신규 공고는 계속 전송하되, 신규가 없더라도 단순한 `신규 없음` 메시지로 성공을 가장하지 않는다. 대신 실패 기관과 성공 기관을 포함한 장애 요약을 보낸다.

```text
⚠️ 임대주택 모니터 수집 오류
기관: SH
단계: 목록 파싱
원인: 공고 행 선택자를 찾지 못했습니다.
정상 처리: LH, GH
```

Telegram 자체가 실패하면 로그와 `runs`에는 실패를 기록하지만 성공한 `deliveries`는 만들지 않는다. 따라서 다음 실행에서 같은 공고를 재시도한다.

## 재시도, 파싱 구조 감지, 로그

HTTP 연결 오류, 타임아웃, HTTP 429, HTTP 5xx는 기관별로 최대 3회 지수 백오프 재시도한다. 인증 오류와 그 밖의 HTTP 4xx는 설정 또는 요청 오류로 간주해 즉시 실패한다. 한 기관의 실패가 다른 기관의 수집과 저장을 중단시키지 않는다.

다음 조건은 `ParserStructureError`로 분류한다.

- HTTP 응답은 성공했지만 예상 목록 컨테이너 또는 필수 JSON 경로가 없음
- 목록 건수가 1건 이상이라고 표시되지만 파싱된 행이 0건
- 후보 공고에서 제목, 공식 URL, 공고일 등 식별에 필요한 필수 필드를 만들 수 없음

실제 검색 결과가 정상적으로 0건인 경우는 구조 실패가 아니다. 수집기는 총 건수 필드, 빈 목록 마커 또는 정상 빈 배열을 통해 이를 구분해야 한다.

로그는 콘솔과 `logs/monitor.log`에 UTC 타임스탬프, 기관, 단계, 재시도 횟수, 예외 유형을 남긴다. Secret과 전체 API 키는 어떤 로그에도 기록하지 않는다. GitHub Actions는 성공 여부와 무관하게 해당 로그를 artifact로 업로드한다.

## GitHub Actions

워크플로는 UTC `03:00`에 실행하여 한국시간 매일 12시를 맞춘다. 수동 실행을 위한 `workflow_dispatch`도 제공한다.

필수 GitHub Secrets:

- `DATA_GO_KR_SERVICE_KEY`
- `TELEGRAM_BOT_TOKEN`
- `TELEGRAM_CHAT_ID`

워크플로는 코드 브랜치를 체크아웃하고, `data` 브랜치에서 DB를 복원하고, Python 3.12 의존성을 설치한 뒤 모니터를 실행한다. 종료 시 DB를 `data` 브랜치에 안전하게 반영하고 로그 artifact를 업로드한다. DB 푸시 충돌은 동시 실행 차단으로 예방하며, 그래도 발생하면 pull/rebase 후 한 번 재시도하고 실패를 로그로 남긴다.

## 테스트 전략

테스트는 실제 외부 서비스를 호출하지 않는다. 공식 응답 형식을 최소화한 JSON과 HTML fixture를 사용한다.

- LH JSON의 필드 정규화, 페이지 처리, 인증·스키마 오류
- SH 목록과 상세 파싱, 빈 목록, 선택자 변경 감지
- GH 임대 및 매입임대 목록 중복 병합, 상세 파싱, 선택자 변경 감지
- 서울·경기 지역과 세 공급유형 필터링
- 후속 게시물 제외와 신혼부부 매입임대 판별
- URL 정규화와 안정적인 고유 키
- SQLite 최초 신규, 기존 공고, 미전송 재시도, 성공 후 중복 방지
- Telegram 메시지 내용과 길이 분할
- HTTP 일시 오류 재시도와 기관별 실패 격리
- 전체 정상·신규 없음 및 일부 기관 실패 실행 요약

구성 파일과 워크플로는 환경변수 누락 오류, cron 값, 권한, concurrency, artifact 업로드를 정적 테스트한다.
