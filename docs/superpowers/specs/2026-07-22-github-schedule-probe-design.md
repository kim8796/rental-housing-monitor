# GitHub 예약 스케줄 진단 및 복구 설계

## 배경

임대주택 모니터는 원격 `main`에 유효한 `13 3 * * *` 예약을 갖고 있지만 저장소 생성 후 `schedule` 이벤트가 한 번도 생성되지 않았다. 수동 실행은 정상이며 저장소와 Actions 설정도 예약 실행 조건을 충족한다. 따라서 애플리케이션이 아닌 GitHub 예약 이벤트 등록·발행 계층을 독립적으로 검사해야 한다.

## 접근 방식

1. 별도 `schedule-probe.yml`을 추가한다. 5분 간격 예약과 수동 실행을 지원하며 현재 시각과 이벤트 이름만 출력한다.
2. 진단 워크플로는 checkout, Python, 저장소 비밀값, Telegram, SQLite 및 쓰기 권한을 사용하지 않는다.
3. `main`에 푸시한 뒤 최대 20분 동안 `event=schedule` 실행 생성을 관찰한다.
4. 예약 실행이 생성되면 프로덕션 워크플로의 예약 등록을 갱신하고 진단 파일을 제거한다.
5. 예약 실행이 생성되지 않으면 GitHub 내부 스케줄러가 이 저장소의 예약을 발행하지 않는 것으로 판정하고, GitHub cron 대신 외부 스케줄러가 기존 `workflow_dispatch`를 호출하도록 전환한다.

## 안전성

- 진단 실행은 텔레그램 메시지를 전송하지 않는다.
- 진단 실행은 운영 SQLite 상태를 읽거나 갱신하지 않는다.
- 진단 실행은 저장소 콘텐츠를 변경하지 않는다.
- 사용자 소유의 기존 미추적 파일은 건드리지 않는다.

## 검증

- 회귀 테스트가 진단 워크플로의 5분 cron, 최소 권한, 무비밀·무운영 의존성을 검사한다.
- 테스트를 먼저 실패시킨 뒤 진단 워크플로를 추가해 통과시킨다.
- 푸시 후 GitHub Actions API에서 해당 워크플로의 `schedule` 이벤트를 직접 조회한다.

## 성공 기준

- 20분 이내 진단 예약 실행이 한 건 이상 생성되거나,
- 생성되지 않은 사실을 API 결과로 확인하여 외부 스케줄러 전환 근거를 확정한다.
