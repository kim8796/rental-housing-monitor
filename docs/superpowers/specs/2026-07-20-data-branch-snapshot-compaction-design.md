# 임대주택 모니터 상태 브랜치 단일 스냅샷 설계

## 목표

1년 이상 매일 실행해도 `data` 브랜치의 Git 이력이 계속 증가하지 않도록 한다. 중복 전송 방지에 필요한 최신 SQLite 상태는 보존하되, 과거 날짜의 DB 스냅샷으로 되돌리는 기능은 제공하지 않는다.

## 현재 구조와 문제

워크플로는 실행 시작 시 `data` 브랜치의 `rental-housing-monitor/data/announcements.db`를 복원하고, 실행이 끝나면 변경된 SQLite 전체 파일을 새 커밋으로 추가한다. DB 자체는 현재 약 49KB로 작지만 바이너리 파일은 Git에서 변경분을 효율적으로 병합하지 못하므로 매일 새 blob과 커밋이 누적된다.

실제 실행시간과 기관 조회 부하는 DB 이력 크기와 무관하다. 개선 대상은 애플리케이션 조회 성능이 아니라 장기 운영 시 불필요하게 증가하는 `data` 브랜치 이력이다.

## 선택한 방식

`data` 브랜치를 감사 로그가 아닌 현재 상태 스냅샷 저장소로 취급한다. 매 실행 후 현재 SQLite 파일 하나만 포함하는 독립 루트 커밋을 만들고, 기존 `data` 브랜치를 `force-with-lease`로 교체한다.

월 1회 압축은 한 달 동안 불필요한 이력이 계속 쌓이고 월별 조건 분기가 추가되므로 사용하지 않는다. GitHub Actions 캐시는 만료 또는 삭제될 수 있어 영속 상태의 유일한 저장소로 사용하지 않는다.

## 보존 정책

- `announcements`: 수집된 공고 키와 정규화 필드를 계속 보존한다.
- `deliveries`: 비식별 전송 대상 키와 성공한 전송 기록을 계속 보존한다.
- `runs`: `started_at`이 현재 UTC 시각 기준 90일 이내인 실행 기록만 보존한다.
- Git 이력: 최신 SQLite 스냅샷을 담은 단일 루트 커밋만 브랜치에서 접근 가능하게 유지한다.
- Actions 로그 artifact: 기존과 같이 14일 보존한다.

공고와 전송 기록은 오래됐다는 이유만으로 삭제하지 않는다. 이를 삭제하면 과거 공고가 공식 페이지에 다시 노출될 때 신규로 잘못 판정될 수 있기 때문이다.

## 실행 흐름

1. `main`을 체크아웃한다.
2. 원격 `data` 브랜치가 있으면 현재 SQLite 파일을 복원한다.
3. LH·SH·GH를 조회하고 Telegram 전송 결과를 SQLite에 반영한다.
4. 완료 시각이 90일보다 오래된 `runs` 행을 삭제한다.
5. SQLite `VACUUM`을 실행해 삭제된 행과 내부 여유 공간을 회수한다.
6. 정리와 `VACUUM`이 성공하면 Actions 작업공간에 일회성 `.ready` 표식을 만든다.
7. 저장 단계는 `.ready` 표식이 있을 때만 DB 파일을 Git blob으로 기록하고, 필요한 하위 tree와 독립 루트 commit을 생성한다.
8. 실행 시작 시 확인한 원격 `data` SHA를 lease 값으로 사용해 새 commit을 `refs/heads/data`에 강제 푸시한다.
9. 원격 SHA가 중간에 바뀌었으면 푸시를 거부하고 워크플로를 실패 처리한다.

기존 `concurrency` 그룹과 `cancel-in-progress: false`는 유지한다. 이는 정상적인 예약 실행끼리 겹치지 않게 하며, `force-with-lease`는 수동 변경이나 예상하지 못한 동시 갱신을 추가로 방어한다.

## 구현 경계

상태 정리와 스냅샷 생성은 두 단위로 분리한다.

- Python 저장소 계층: `AnnouncementRepository.compact()`가 `runs` 보존 기간 정리와 `VACUUM`을 수행한다. CLI는 성공·실패 여부와 관계없이 저장소를 닫기 직전에 이를 호출하고, 성공한 경우에만 일회성 `.ready` 표식을 만든다.
- 스냅샷 스크립트: `rental-housing-monitor/scripts/persist_data_snapshot.sh`가 DB 하나로 독립 tree/commit을 생성하고 lease 기반 푸시를 수행한다.
- GitHub Actions 저장 단계: DB와 `.ready` 표식이 모두 있으면 스냅샷 스크립트를 호출하고 결과를 그대로 성공 또는 실패로 반영한다. 표식 자체는 스냅샷에 넣지 않는다.

애플리케이션의 기관 수집, 신규 판정, Telegram 전송 순서는 변경하지 않는다. `main` 브랜치 이력에는 영향을 주지 않으며 `data` 브랜치만 기계 생성 스냅샷으로 교체한다.

## 오류 처리

- DB 파일이 생성되지 않았으면 기존처럼 저장 단계를 종료한다.
- SQLite 정리 또는 `VACUUM`이 실패하면 `.ready` 표식이 생성되지 않으므로 기존 `data` 브랜치를 유지하고 워크플로를 실패 처리한다.
- 원격 `data` 브랜치가 없으면 lease 없이 최초 스냅샷을 생성한다.
- 원격 `data` SHA가 예상과 다르면 `force-with-lease`가 푸시를 거부하며 기존 상태를 덮어쓰지 않는다.
- 모니터 실행이 일부 실패해도 생성된 DB가 있으면 실행 상태와 성공한 전송 기록을 보존한다.
- Telegram 전송 중 일부가 성공한 뒤 실패한 경우에도 성공 기록을 저장해 다음 실행의 중복 전송을 막는다.

## 테스트 전략

- 저장소 테스트에서 90일보다 오래된 `runs`만 삭제되고 최신 실행은 유지되는지 확인한다.
- 공고와 전송 기록이 정리 과정에서 삭제되지 않는지 확인한다.
- 테스트용 SQLite에 정리와 `VACUUM`을 적용한 뒤 DB를 다시 열 수 있는지 확인한다.
- 워크플로 정적 테스트에서 누적형 `origin/data` worktree 커밋 방식이 제거됐는지 확인한다.
- 워크플로 정적 테스트에서 독립 commit 생성과 `force-with-lease` 사용을 확인한다.
- 임시 bare 저장소를 이용한 스냅샷 스크립트 테스트에서 반복 저장 후 `data` 브랜치 커밋 수가 1개인지 확인한다.
- 배포 후 수동 Actions 실행으로 수집, Telegram 신규 없음 메시지, DB 복원, 단일 스냅샷 갱신을 검증한다.

## 배포와 확인

변경을 `main`에 푸시한 뒤 수동 `workflow_dispatch`를 한 번 실행한다. 성공 조건은 다음과 같다.

- 모니터 단계와 상태 저장 단계가 모두 성공한다.
- 운영 로그가 `status=success`를 기록한다.
- `data` 브랜치의 접근 가능한 이력이 단일 commit이다.
- SQLite의 공고·전송 건수가 실행 전보다 의도치 않게 감소하지 않는다.
- SQLite에 원시 Telegram chat ID가 다시 저장되지 않는다.

이후 예약 실행은 기존과 동일하게 매일 한국시간 12시에 수행한다.
